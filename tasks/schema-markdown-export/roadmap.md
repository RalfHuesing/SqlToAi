# Roadmap: Database schema export to Markdown

Implement the [concept](Konzept.md) in the order below. Its scope and exclusions are binding. The roadmap was created at the user's explicit request for step 2 while the concept remains `draft`; this does not start implementation or change the concept's approval status.

Each implementation item includes inspection of the current code, focused xUnit v3 tests, relevant documentation updates, and an atomic Conventional Commit in German. Use the repository's AiNetCodeNavigator workflow for C# navigation and preserve unrelated working-tree changes. Only mark an item complete after its acceptance criteria have been verified; record brief validation evidence with that item.

The concept's [model/role assignment](Konzept.md#implementation-roles-and-model-assignment) and [presentation boundary](Konzept.md#presentation-boundary-and-mcp-output-preservation) are binding for stage 3. Dispatch Sol `high` for items 1–2 and 4, Sol `medium` for item 3, and two separate sequential Luna `high` agents for item 5's reviews. Assign corrections with the effort required by their affected boundary. Record the actual model/effort with each delegated item's evidence; do not silently fall back to another model. Implementation starts only when explicitly invoked.

- [x] **2. Explicit offline presentation with unchanged MCP output**
  - **Intention:** Make schema documents usable offline while preserving existing MCP output exactly.
  - **Scope:** Inspect the current service/rendering boundary and record the architectural choice from the concept: prefer an immutable per-call rendering context with existing MCP defaults; use a narrow offline renderer over shared typed schema data/formatting primitives if a context would entangle concerns or spread branches. Implement that choice through application services. The export path omits metadata descriptions, the `Anonymized` column, and metadata/policy/rule-provider calls before rendering. It omits MCP invocation instructions or substitutes local references supplied by the shared path mapping. Retain SQL comments and existing unavailable-definition notes. Link trigger overviews to their files using structured inputs. The MCP entry points, tool parameters, defaults, complete content, and error results remain unchanged.
  - **Not:** No Markdown parsing/string-replacement workaround, mutable singleton rendering mode, global configuration switch, duplicated schema queries, reconstructed table DDL, additional schema fields, or generic rendering/export framework.
  - **Architecture decision (before implementation):** Use an immutable per-call `SchemaRenderingContext` carrying the current typed object and a copied object-to-path mapping. Existing MCP entries call the shared rendering core without that context. Dedicated application-service export entries pass it before enrichment and use the same catalog/data queries and Markdown table formatter. Only the column/enrichment and navigation presentation need bounded branches; an additional renderer/data model would duplicate composition without improving separation. Structured trigger IDs and foreign-key schema/name fields supply local links; no rendered Markdown is parsed or rewritten. Ten fixed full-content/note/error regression cases passed against the unchanged implementation before this refactoring, including original SQL newlines and comments.
  - **Acceptance:** Focused renderer/service tests show that the export path invokes no metadata/policy/rule providers, including when central rules are enabled, and emits neither descriptions nor the `Anonymized` column. SQL definitions retain their comments and unavailable-definition notes. Export-generated navigation text contains no instructions to invoke MCP tools; comments inside original SQL are preserved. Capture representative pre-change MCP results under fixed inputs/data; full deterministic content, notes, and errors remain identical after refactoring and after interleaved offline calls. Evidence explains the selected presentation boundary and why it avoids workarounds and duplicate data retrieval. Relevant tests and the solution build pass.
  - **Completion evidence:** Implemented by `gpt-6.1-sol`, reasoning effort `high`. [SchemaRenderingContext](../../src/SqlToAi/Database/SchemaRenderingContext.cs) copies/freeze-stores typed identities and supplied paths per call; no ambient/global mode or mutable service state was added. Three dedicated export service entries reuse existing access checks, query/error boundaries and renderers. Offline column rendering skips metadata and anonymization enrichment before calling any provider. Discovery instructions are omitted for tables/views and replaced with a parameter count for routines. Trigger object IDs, foreign-key schema/name fields and referencing-entity fields drive escaped relative links; missing targets remain text. Original SQL comments/newlines and successful unavailable-definition notes are retained.

- [x] **3. CLI export, file composition, and user documentation**
  - **Intention:** Deliver `SqlToAi.exe export-schema --database <name> --output <directory>` using the existing executable, configuration, dependency injection, access checks, logging, and schema services from items 1 and 2.
  - **Scope:** Register the command with exactly the two required inputs. Coordinate typed discovery, shared schema/detail calls, document composition, and UTF-8 file output. Follow the concept's directory layout and per-kind content: tables/views include columns, incoming/outgoing foreign keys, indexes, constraints, static referencing entities, and linked trigger overviews; views additionally include SQL definitions; procedures/functions include definitions and parameter details; trigger files identify their parents and include their definitions. Create a small relative-link `README.md` grouped by kind, without empty kind directories.
  - **File/error contracts:** Use one deterministic, Windows-safe object-to-path mapping for filenames and all links. Preserve original SQL names in headings and the overview. Validate an absent or empty output directory and check every planned path for case-insensitive collisions before writing any files. Stop at the first failed service result or filesystem error, returning a nonzero exit code and leaving any files already written. Do not roll back or clean up; a repeat run needs a new or manually emptied directory. Successful unavailable-definition notes remain in the files and permit exit code zero when the remaining operations succeed.
  - **Not:** No MCP server startup/protocol call, new MCP export tool, extra options, overwriting, cleanup, data extraction, snapshot/report generation, or duplicated schema queries/formatting primitives. Existing `server` and `query` commands remain available with unchanged output.
  - **Acceptance:** CLI tests cover missing inputs and success/failure exit codes. Export tests verify the expected file set for every supported kind and more objects than the interactive search limit, composition of table details and routine parameters, trigger-parent links, and navigation from `README.md`. File tests cover new/empty/nonempty targets, Windows-invalid/reserved names, case collisions rejected before the first write, escaped relative links, failed service calls, file-writing failures, remaining partial output, and rejection of a repeat run into that nonempty directory. Existing successful unavailable-definition results are written as notes rather than treated as failures. Tests also cover omitted provider calls and retained SQL comments through the export entry point. Update [README.md](../../README.md), [development.md](../../docs/development.md), and [architecture.md](../../docs/architecture.md) with invocation, included content, exclusions, empty-directory requirements, and failure behavior. `dotnet build SqlToAi.slnx` and `dotnet test SqlToAi.slnx` pass with the repository's required quality checks.
