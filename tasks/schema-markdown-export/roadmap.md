# Roadmap: Database schema export to Markdown

Implement the [concept](Konzept.md) in the order below. Its scope and exclusions are binding. The roadmap was created at the user's explicit request for step 2 while the concept remains `draft`; this does not start implementation or change the concept's approval status.

Each implementation item includes inspection of the current code, focused xUnit v3 tests, relevant documentation updates, and an atomic Conventional Commit in German. Use the repository's AiNetCodeNavigator workflow for C# navigation and preserve unrelated working-tree changes. Only mark an item complete after its acceptance criteria have been verified; record brief validation evidence with that item.

- [ ] **1. Shared object discovery and unambiguous trigger resolution**
  - **Intention:** Supply the exporter with object identities from the existing schema infrastructure, without parsing Markdown or duplicating catalog queries.
  - **Scope:** Extract/reuse the existing object discovery in the schema layer. Expose typed identities for every supported object kind, including SQL schema, object name, kind, and the parent association needed for DML triggers. The export path must enumerate the supported objects without the interactive result limit; the existing object search must retain its filtering, limit, ordering, and Markdown output. Apply existing database access checks to the new service entry. Correct the shared trigger operation so parent validation and definition retrieval use the same trigger identity, retaining compatibility with existing MCP callers.
  - **Not:** No export-only catalog/trigger query, arbitrary large search limit, new object kinds, or dependency analysis.
  - **Acceptance:** A known object set covers tables, views, SQL procedures, scalar functions, inline table-valued functions, table-valued functions, and table/view DML triggers. A set larger than the interactive default limit is returned without truncation on the export path, while interactive search retains its limit. Denied database access returns the existing failure result; `SchemaOnly` access permits schema discovery. Trigger tests cover a non-`dbo` schema, identical trigger names in different schemas, correct parent association, and existing MCP callers. Relevant schema/search regression tests and the solution build pass.

- [ ] **2. Shared rendering for offline schema documents**
  - **Intention:** Make the existing schema Markdown usable offline without tool-configuration enrichment or a second renderer.
  - **Scope:** Add the small shared rendering adjustments required by the concept through the schema services. The export path omits metadata descriptions, the `Anonymized` column, and metadata/policy/rule-provider calls. It omits MCP invocation instructions or substitutes local section/file references where the exporter supplies them. Reuse the current column, view, routine, and detail renderers; retain SQL comments in original definitions and existing unavailable-definition notes. Allow the export coordinator to link trigger overviews to the corresponding trigger files without parsing rendered Markdown. The default MCP path retains its descriptions, anonymization indicators, rule handling, and discovery instructions.
  - **Not:** No metadata filtering after rendering, new policy abstraction, reconstructed table DDL, additional schema fields, or generic rendering/export framework.
  - **Acceptance:** Focused renderer/service tests show that the export path invokes no metadata/policy/rule providers, including when central rules are enabled, and emits neither descriptions nor the `Anonymized` column. SQL definitions retain their comments and unavailable-definition notes. Export-generated navigation text contains no instructions to invoke MCP tools; comments inside original SQL are preserved. MCP regression tests confirm the previous enrichment and discovery output. Relevant tests and the solution build pass.

- [ ] **3. CLI export, file composition, and user documentation**
  - **Intention:** Deliver `SqlToAi.exe export-schema --database <name> --output <directory>` using the existing executable, configuration, dependency injection, access checks, logging, and schema services from items 1 and 2.
  - **Scope:** Register the command with exactly the two required inputs. Coordinate typed discovery, shared schema/detail calls, document composition, and UTF-8 file output. Follow the concept's directory layout and per-kind content: tables/views include columns, incoming/outgoing foreign keys, indexes, constraints, static referencing entities, and linked trigger overviews; views additionally include SQL definitions; procedures/functions include definitions and parameter details; trigger files identify their parents and include their definitions. Create a small relative-link `README.md` grouped by kind, without empty kind directories.
  - **File/error contracts:** Use one deterministic, Windows-safe object-to-path mapping for filenames and all links. Preserve original SQL names in headings and the overview. Validate an absent or empty output directory and check every planned path for case-insensitive collisions before writing any files. Stop at the first failed service result or filesystem error, returning a nonzero exit code and leaving any files already written. Do not roll back or clean up; a repeat run needs a new or manually emptied directory. Successful unavailable-definition notes remain in the files and permit exit code zero when the remaining operations succeed.
  - **Not:** No MCP server startup/protocol call, new MCP export tool, extra options, overwriting, cleanup, data extraction, snapshot/report generation, or catalog/rendering duplication. Existing `server` and `query` commands remain available.
  - **Acceptance:** CLI tests cover missing inputs and success/failure exit codes. Export tests verify the expected file set for every supported kind and more objects than the interactive search limit, composition of table details and routine parameters, trigger-parent links, and navigation from `README.md`. File tests cover new/empty/nonempty targets, Windows-invalid/reserved names, case collisions rejected before the first write, escaped relative links, failed service calls, file-writing failures, remaining partial output, and rejection of a repeat run into that nonempty directory. Existing successful unavailable-definition results are written as notes rather than treated as failures. Tests also cover omitted provider calls and retained SQL comments through the export entry point. Update [README.md](../../README.md) and [architecture-spec.md](../../docs/architecture-spec.md) with invocation, included content, exclusions, empty-directory requirements, and failure behavior. `dotnet build SqlToAi.slnx` and `dotnet test SqlToAi.slnx` pass with the repository's required quality checks.

- [ ] **4. Final audit and demo export verification**
  - **Intention:** Check the delivered behavior against the concept and confirm that an agent can navigate the files offline.
  - **Scope:** Perform the final read-only audit of code, tests, documentation, and completion evidence. Check shared-service/query/renderer reuse, database access checks, the shared trigger correction, preservation of MCP behavior, the required omissions, and all export/file/error contracts. Confirm the known-object tests exercise every supported kind and a set above the interactive search limit. Run the implemented command against the configured demo database into a new or empty directory; inspect a table, a view, and an available trigger/routine and follow their local links without MCP access. Demo verification must not read business records or mutate the database.
  - **Not:** No new feature work, production-code changes by the auditor, sample-data export, completeness report, or new task/report files.
  - **Acceptance:** The audit has no unresolved findings against the concept; the final solution build/tests and required checks are green. The demo export demonstrates readable object files and working local navigation, with no metadata/anonymization indicators or generated MCP invocation instructions. Record concise validation evidence and the outcome with the roadmap items. If the configured demo database is unavailable, do not claim this verification or mark the final audit complete.
